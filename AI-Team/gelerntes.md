# Gelerntes — projektgebunden

Lehren, die an dieses Projekt gebunden sind und mehrere Rollen betreffen. Lehren einer einzelnen Rolle stehen in `AI-Team/<rolle>.md`; allgemeine Lehren schlägt der Director für die Factory vor.

- **2026-11-24 (#1, Security-Review)**: Das geprüfte Repo ist fremd. Seine `.git/config` und `.gitattributes` können beim Lesen Programme starten: `log.showSignature` + `gpg.program`/`gpg.ssh.program` (bei `git log`/`show`), und für Diffs zusätzlich `diff.external`, `diff.<treiber>.textconv`/`command` über `.gitattributes`. Jeder git-Aufruf von gitreviewA setzt deshalb `-c log.showSignature=false` und bei Diffs `--no-ext-diff --no-textconv`; jede Karte mit neuem git-Aufruf bekommt einen Test mit Marker-Skript im Wegwerf-Repo. Gilt für entwickler, planer, code-reviewer, security-reviewer.

- **2026-11-24 (#21, Entwicklertest)**: gitreviewA wird typischerweise von einer KI aus einem nicht-interaktiven Skript im Hintergrund gestartet (`… & pid=$!`). Dort erbt der Prozess **ignoriertes SIGINT** (`SigIgn` in `/proc/<pid>/status`). Tests, die über Node/Python starten, sehen das nicht — für Signal- und Startverhalten mindestens einen Test mit Start über `bash -c '… &'` fahren. Gilt für entwickler, entwicklertester, code-reviewer.

- **2026-11-24 (#5, Security-Review)**: Das fremde Repo kann die Anzeige auch ohne Programmstart verfälschen: `refs/replace` (Ersatzcommit unter echtem Hash) → `GIT_NO_REPLACE_OBJECTS=1` in `GitStart`; `.gitmodules`/`diff.ignoreSubmodules` blendet Submodul-Änderungen aus → `--ignore-submodules=none` bei jedem diff/show. Pfade und Namen aus dem Repo zeigen Bidi-/Formatzeichen sichtbar markiert (`⟨U+202E⟩`). Gilt für entwickler, planer, code-reviewer, security-reviewer.

- **2026-11-24 (#2, Reviews)**: git löst Namen vor Hash-Präfixen auf — ein Tag `97f3` im fremden Repo lenkt den Präfix `97f3` auf einen anderen Commit; jede Hexfolge aus Aufruf oder stdin wird nach dem Lesen gegen den gelieferten `%H` geprüft. Wegwerf-Repos in Tests staffeln Commit-Zeiten — für Reihenfolge-Kriterien zusätzlich einen Test mit gleichen Zeiten fahren (KI-Commits entstehen in derselben Sekunde). Gilt für entwickler, code-reviewer, security-reviewer.

- **2026-11-24 (#6, Code-Review)**: gitreviewA nimmt den Aufrufordner als git-Arbeitsordner — Pathspec-Aufrufe hängen damit vom Startordner ab. Jeder neue git-Aufruf mit Pfad bekommt einen Test mit Start aus einem Unterordner des Repos. Gilt für entwickler, code-reviewer, entwicklertester.

- **2026-11-24 (#17, Security-Review)**: Jede Ausgabe fremder Namen, ob Oberfläche, Protokoll oder Ergebnis auf stdout, markiert unsichtbare und richtungsändernde Zeichen mit derselben Klasse `Fremdtext/UnsichtbareZeichen` (Runes: Steuerzeichen außer Tab, Cf, U+2028/2029, einzelne Surrogate). Keine zweite Zeichenliste je Ausgabe. Das Ergebnis auf stdout ist eine Ausgabe wie jede andere: Ein Pfad, der in der Oberfläche markiert ist, war dort roh. Jede Karte, die fremde Namen ausgibt, bekommt einen Test mit U+202E, U+200B und U+E0041 bis in diese Ausgabe. Gilt für entwickler, planer, code-reviewer, security-reviewer.

- **2026-11-24 (#16, Security-Review)**: Namen aus dem fremden Repo sind Bytes, kein Text. Jede git-Ausgabe läuft durch `Fremdtext/FremdeBytes` (ungültige Bytes als `⟨0xFF⟩`, verlustfrei); jeder Schlüssel aus Namen (Haken, Anmerkungen, später Zusammen-Ansicht) bekommt einen Test mit `f\xFF.txt` und `f\xFE.txt` (angelegt über python3), und ein Name mit Marke wird nie als Pfad-Argument an git gegeben (#28). Gilt für entwickler, planer, code-reviewer, security-reviewer.

- **2026-11-24 (#16, Nacharbeit)**: Aufräumen nur mit eigenen, festen Pfaden — nie `rm -rf /tmp/gitreviewa-test-*` mit Platzhalter: dort liegen die Temp-Repos laufender Tests anderer Rollen. Gilt für alle bauenden und prüfenden Rollen.

- **2026-11-24 (#28, Security-Review)**: Fremde Konfiguration startet Programme auch über Wege ohne Diff: `git check-attr` liest den Index und startet `core.fsmonitor`; in einem Partial-Clone startet jeder Blob-Zugriff (`--numstat`, `-p`) einen Lazy-Fetch über `remote.*.uploadpack`/`core.sshCommand`. Abwehr zentral in `GitStart`: `-c core.fsmonitor=false` und `GIT_NO_LAZY_FETCH=1`; die Marker-Probe gehört für jeden neuen Aufruf dazu, auch für Hilfsaufrufe wie `check-attr`. Wer Namen über stdin an git gibt, prüft **jeden** Namen der Zeile auf LF und CR (git trennt an LF und schneidet CR ab), nicht nur den mit Rohbytes. Gilt für entwickler, planer, code-reviewer, security-reviewer.

- **2026-11-25 (#10, Reviews)**: Ein neuer git-Lesepfad erbt die Schutzmaßnahmen nicht automatisch. `GitStart` trägt nur den Prozess- und Konfigurationsschutz; **Ausgabegrenze** (`Ausgabegrenze.Standard`) und **Namensprüfung** (`Namenspruefung`, LF/CR in jedem Namen auf stdin) hängen an der Aufrufstelle. Der Netto-Diff aus #10 hatte beides nicht: 28 MB Antwort und ein über LF eingeschleuster zweiter Pfad, der den Patch einer anderen Datei lieferte. Je neuem Lesepfad gehört eine Probe mit kleiner Grenze und eine mit LF/CR im Namen dazu.

- **2026-11-25 (#7, Bau)**: Keine künstliche Last erzeugen. Ein entwickler startete für den Nachweis „wackelt nicht unter Last“ ein Skript mit `while :; do :; done`-Schleifen (`nice -n 19`), die Rechnerlast stieg auf ~8 bei Grenze 6,0 (Betreiber: 75 %), und nach einem Hinweis startete er es erneut. Wackel-Nachweise laufen mit der echten Last der parallelen Rollen: mehrere volle Läufe `--workers=2` nacheinander, Ursache am Test/Code begründet. Die Lastgrenze gilt für alles, was eine Rolle startet.

- **Keine Last erzeugen, um Wackler zu reproduzieren** (Director 2026-11-26, #58): Der Auftrag „zusammen mit schweren Specs fahren, damit er unter Last kippt“ war faktisch künstliche Last — Rechner bei Last 18, Betreiber am Gerät. Wackler werden mit dem einzelnen Test wiederholt und im Code gesucht (Rennen, Lesen vor dem eingeschwungenen Zustand), nie durch absichtliche Parallellast.

- **Keine harten Performance-Ziele** (Betreiber 2026-11-26: „Wir brauchen so harte Performance-Bedingungen nicht. Bisher gesehen war die Performance für die real-Nutzung vollkommen in Ordnung. Wenn es Probleme gibt melde ich mich.“): planer plant keine Zeitkriterien mit engen Margen (kein 0,7-s-Ziel mit 30-%-Abstand), nur grobe Schranken gegen echte Einbrüche (Größenordnung Sekunden); Reviews werten Zeitmessungen nicht als Muss, außer die Oberfläche friert spürbar ein; Leistungsarbeit nur auf Meldung des Betreibers.
