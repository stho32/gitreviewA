# User Story R00048: Commit-Angaben unverfälscht und begrenzt lesen

**Als** prüfender Mensch (oder die KI, die für ihn `gitreviewA` aufruft)
**möchte ich** Autor, Datum, Betreff und Message jedes Commits genau so sehen, wie sie im Commit stehen, und bei übergroßen Angaben eine klare Meldung bekommen,
**damit** ein fremdes Repository mir weder ein falsches Datum oder einen falschen Betreff unterschieben noch den Lauf mit Megabytes lahmlegen kann.

Vorbereitung für alle Szenarien (Wegwerf-Repo im Temp-Ordner, nie das Projekt-Repo; Linux; Programm immer mit `--kein-browser`). ␟ steht für das Byte 0x1F, ␞ für 0x1E. „Die Leiste liefert“ heißt: `GET /api/commits` (oder der Aufruf-Interactor im Integrationstest) liefert diese Felder.

**Repo F** (herstellbar mit `git` und `python3`, geprobt mit git 2.48.1):

```bash
git init -q -b main F && cd F
git config user.name "Carla Beispiel"; git config user.email carla@example.org
printf 'a\n' > a.txt; git add a.txt
GIT_AUTHOR_DATE=2026-03-03T08:00:00+01:00 git commit -q -m "Start"                                   # p
printf 'b\n' > b.txt; git add b.txt
GIT_AUTHOR_NAME=$'Anna\x1fBeispiel' GIT_AUTHOR_DATE=2026-03-04T09:15:00+01:00 \
  git commit -q -m $'Betreff\x1fmit Trenner' -m $'Rumpf\x1fmit Trenner'                              # t
printf 'c\n' > c.txt; git add c.txt
GIT_AUTHOR_NAME=$'Bernd\x1eBeispiel' GIT_AUTHOR_DATE=2026-03-05T18:30:00+01:00 \
  git commit -q -m $'Zweiter\x1e' -m $'Zeile eins\x1f\x1f\nZeile zwei'                               # u
printf 'tree %s\nparent %s\nauthor Dora Beispiel <dora@example.org> 1772700000 +0100\ncommitter Dora Beispiel <dora@example.org> 1772700000 +0100\n\nVor dem NUL\000danach\n\nRumpf\n' \
  "$(git rev-parse HEAD^{tree})" "$(git rev-parse HEAD)" > ../nul-commit.txt
z=$(git hash-object -t commit -w --literally ../nul-commit.txt); git update-ref refs/heads/nul "$z"    # z (Message mit NUL)
python3 -c "import sys; sys.stdout.write('Riesig\n\n' + ('y'*1023+'\n')*(9*1024))" > ../gross.txt
printf 'd\n' > d.txt; git add d.txt; GIT_AUTHOR_DATE=2026-03-06T10:00:00+01:00 git commit -q -F ../gross.txt   # g (Message 9 MiB)
p=$(git rev-parse HEAD~3); t=$(git rev-parse HEAD~2); u=$(git rev-parse HEAD~1); g=$(git rev-parse HEAD)
```

**Repo W** (für die Ansichten, Grenze 4 KiB als Testparameter): Commit `p` „Start“ mit `a.txt`, danach Commit `w` „Viele Dateien“, der 200 Dateien `datei-000-<32 × x>.txt` … `datei-199-<32 × x>.txt` (je 1 Zeile, Pfad 46 Zeichen) hinzufügt. Für „nur die Elternfolge zu groß“ zusätzlich ein Merge `m` mit 120 Eltern über `git commit-tree -p … -p …` (Ausgabe der Elternfolge etwa 5 KiB).

## Szenario 1: Trennzeichen im Autor verschiebt nichts (Abnahme-Probe)
**Gegeben** Repo F
**Wenn** `gitreviewA $t` startet
**Dann** liefert die Leiste für `t` Autor `Anna␟Beispiel`, Datum `2026-03-04T09:15:00+01:00`, Betreff `Betreff␟mit Trenner`, Message `Rumpf␟mit Trenner` (heute: Autor `Anna`, Datum `Beispiel`, Betreff `2026-03-04T09:15:00+01:00`).

## Szenario 2: Jede Auswahlart liest dieselben Felder
**Gegeben** Repo F
**Wenn** nacheinander `gitreviewA $u $t`, `gitreviewA $p..$u`, `gitreviewA $p..$t $p..$u` und `printf '%s\n' $u $t | gitreviewA -` starten
**Dann** liefert jede Leiste genau `u`, dann `t`; `t` wie in Szenario 1, `u` mit Autor `Bernd␞Beispiel`, Datum `2026-03-05T18:30:00+01:00`, Betreff `Zweiter␞`, Message `Zeile eins␟␟` und `Zeile zwei` in zwei Zeilen.

## Szenario 3: NUL in der Message
**Gegeben** Repo F
**Wenn** `gitreviewA $z` startet
**Dann** startet der Lauf, und die Leiste liefert Autor `Dora Beispiel`, Datum `2026-03-05T09:40:00+01:00`, Betreff `Vor dem NUL` und eine leere Message — wie `git log` selbst, ohne Fehler und ohne verschobene Felder.

## Szenario 4: Zu große Commit-Angaben beim Start
**Gegeben** Repo F und die Produktgrenze 8 MiB
**Wenn** `gitreviewA $g` startet (ebenso `gitreviewA $u..$g` und `printf '%s\n' $g | gitreviewA -`)
**Dann** endet der Prozess mit Exit 2 ohne Server, stdout bleibt leer, und stderr trägt genau eine Fehlerzeile, die die Grenze von 8 MiB nennt und nicht „nicht auflösbar“ sagt; `gitreviewA $t $u` startet weiter.

## Szenario 5: Grenze knapp darunter und darüber
**Gegeben** eine Grenze von 4 KiB (Testparameter) und je ein Commit mit 3 KiB und 5 KiB Message
**Wenn** je ein Lauf damit startet
**Dann** startet der erste mit der ganzen Message, der zweite wird wie in Szenario 4 abgewiesen.

## Szenario 6: Zu große Dateiliste in „Einzeln“
**Gegeben** Repo W, Grenze 4 KiB, Lauf `gitreviewA $w $p`
**Wenn** der Mensch in „Einzeln“ den Commit `w` wählt
**Dann** zeigt die Dateiliste den Fehlerzustand mit dem Grund „zu groß“ und der Grenze — keine leere Liste, nicht „Keine Dateien geändert“; die Wahl von `p` zeigt dessen Datei `a.txt`; stderr trägt eine Warnung mit dem Kurz-Hash von `w`.

## Szenario 7: Zu große Angaben in „Zusammen“, beim Abhaken und im Ergebnis
**Gegeben** Repo W, Grenze 4 KiB, Lauf `gitreviewA $w $p`
**Wenn** die Ansicht „Zusammen“ (Standard) lädt, der Mensch danach eine Datei von `w` abhaken will und den Lauf beendet
**Dann** zeigt „Zusammen“ den Fehlerzustand mit dem Grund „zu groß“, das Abhaken wird mit diesem Grund abgelehnt (kein Haken gesetzt), und das Ergebnis nennt Zitate als nicht lesbar statt sie still wegzulassen; dasselbe gilt für einen Lauf mit `m`, in dem nur die Elternfolge die Grenze überschreitet.

## Szenario 8: Jeder Leser endet an der Grenze
**Gegeben** die Tabelle aller Leser aus R00048 (Ursachenanalyse) und je Leser eine Grenze unter seiner Ausgabe
**Wenn** jeder Leser einzeln läuft
**Dann** endet jeder mit dem Ausgang „zu groß“, am einen Leseort sind höchstens Grenze + 80 KiB gelesen, und danach läuft kein git-Prozess mehr.
